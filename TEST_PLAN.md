## 1. Область проверки

По заданию: **каталог - корзина - оформление заказа**, плюс вход и регистрация
в том объёме, в каком они нужны для этого пути.

Выбрана версия `sprint5`, а не `sprint5-with-bugs`: в последней есть только
монолитный `checkout` без шагов корзины и адреса, поэтому обязательную цепочку
«корзина - оформление заказа со способом оплаты» там нельзя пройти целиком.
`sprint5` содержит шаги `cart`, `login`, `address`, `payment`.

### В области проверки

| Подобласть | Что проверяется |
|---|---|
| Каталог | список товаров, поиск, фильтр по цене, сортировка по цене, карточка товара |
| Корзина | добавление, изменение количества, удаление, слияние одинаковых позиций, бизнес-правило «один Thor Hammer», границы количества |
| Оформление | шаги checkout, адрес и его автозаполнение по postcode, способ оплаты cash-on-delivery, создание заказа, номер счёта, сохранённые суммы и позиции |
| Доступ | изоляция заказов между покупателями, обязательность аутентификации, валидация запроса |
| Данные | остаток товара, количество сверх остатка, пустая корзина, чужая корзина |
| Вход | регистрация и логин через API, логин через форму, блокировка после неудачных попыток |

### Вне области проверки (сознательно)

- **Админка** (`/admin`): CRUD, отчёты, статистика.
- **Аренда** (rentals) - отдельная витрина с иной логикой ценообразования.
- **Контактная форма** и чат-виджет.
- **Социальный вход** (Google/GitHub) - требует внешних провайдеров.
- **2FA/TOTP**, восстановление и смена пароля, профиль.
- **PDF-инвойсы и email-уведомления** (MailCatcher поднят, но не проверялся).
- **Кросс-браузерность**: прогон только в Chromium, проектов Firefox/WebKit нет.
- **Производительность, нагрузка, rate limiting**.
- **i18n** (переключение языка).

Причина: 4 часа. Админка и аренда прямо исключены заданием; остальное не влияет
на путь «найти товар - положить в корзину - оформить заказ».

## 2. Риски и приоритеты

Ранжирование по «вероятность × цена ошибки». Приоритет тест-кейсов выводится
из этой таблицы.

| ID | Риск | Влияние | Приоритет |
|---|---|---|---|
| R1 | Заказ принимается при нулевом остатке или в количестве больше остатка | Продажа несуществующего товара, отрицательный остаток, отмены и возвраты | **Критический** |
| R2 | Заказ создаётся с пустой корзиной или на нулевую сумму | Мусорные счета, искажение отчётности и рассылок | **Высокий** |
| R3 | Сумма заказа не совпадает с корзиной (цена, количество, скидка) | Финансовые расхождения и претензии | **Высокий** |
| R4 | Пользователь не может завершить оформление в UI | Потеря продаж, обращения в поддержку | **Высокий** |
| R5 | Покупатель видит или оплачивает чужую корзину/заказ | Утечка данных, репутационный ущерб | **Высокий** |
| R6 | Адрес принимается в противоречивом виде | Недоставка, ручная правка заказов | Средний |
| R7 | Поиск, фильтр или сортировка возвращают не то, что просили | Пользователь не находит товар | Средний |
| R8 | Ошибки API отдаются как 5xx или без понятного текста | Инцидент нельзя разобрать по логам | Средний |
| R9 | Автотесты нестабильны или зависят от порядка | Доверие к прогону падает, дефекты пропускаются | Средний |

Оценка R4 подтвердилась на практике: кнопка **Confirm** в этой сборке требует
двух нажатий (BUG-05), причём первое показывает «Payment was successful».
Это ровно тот класс риска, который не виден в API-тестах.

## 3. Порядок проверки

1. **Развёртывание** и подготовка данных (вне бюджета 4 часов).
2. **Анализ**: user stories, `docs/features.md`, контракты API, `data-test`-атрибуты,
   бизнес-правила из кода.
3. **Критический путь через API**: заказ - чтение заказа - сверка суммы и позиций.
4. **Корзина**: количество, удаление, слияние, Thor Hammer, границы.
5. **Каталог**: инварианты поиска, фильтра и сортировки.
6. **Доступ**: чужой заказ, обязательность токена, валидация.
7. **UI критический путь**: мастер оформления.
8. **Исследовательские пробы** на границах: остатки, пустая корзина, чужая корзина,
   кеш после reseed - здесь найдены BUG-01 ... BUG-04 и BUG-06.
9. **Регрессии на дефекты** с `test.fail()`.
10. **Документы и решение о релизе.**

## 4. Подход к тестовым данным

- **Свой покупатель на каждый тест.** Регистрация через `POST /users/register`
  с уникальным e-mail. Демо-аккаунты не используются: после трёх неудачных
  попыток аккаунт блокируется (проверено, TC-30), и общий пользователь
  превратил бы один негативный тест в каскад падений.
- **База между тестами не сбрасывается.** Каждый тест создаёт свою корзину и
  свой заказ, поэтому набор не зависит от предыдущих запусков и от порядка
  выполнения. Проверено последовательным, параллельным и случайным прогоном.
- **Перед прогоном рекомендуется `migrate:fresh --seed` + `cache:clear`**:
  заказы уменьшают остаток, а кеш каталога живёт 300 секунд (BUG-06).
- **Товар для теста подбирается по факту наличия**: список кешируется, поэтому
  фикстура перепроверяет `GET /products/{id}` и берёт товар, который реально
  есть на складе.
- **Адрес строится из `GET /postcode-lookup`**, а не выдумывается: API проверяет
  соответствие города/региона стране, и придуманный адрес даёт 422, который
  легко принять за дефект продукта.

## 5. Допущения

| # | Допущение | На чём основано |
|---|---|---|
| A1 | Товар с `in_stock: false` (остаток 0) заказать нельзя | Флаг в API, заблокированная кнопка «Add to cart» в UI |
| A2 | Количество в заказе не может превышать остаток | Стандартное поведение магазина; ТЗ требует проверять корректность данных |
| A3 | Заказ с пустой корзиной недопустим | UI не показывает переход при пустой корзине; заказ на 0.00 не имеет смысла |
| A4 | Корзина принадлежит тому, кто её создал | Ожидание пользователя; в API корзина анонимна (BUG-04) |
| A5 | Остаток 25 у hand tools - значение сидера, а не бизнес-константа | `database/seeders/ProductSeeder.php` |
| A6 | Блокировка наступает на третьей неудачной попытке и не действует на администратора | `UserService::MAX_LOGIN_ATTEMPTS = 3`, проверено вручную (TC-30) |

## 6. Открытые вопросы к продукту

| # | Вопрос | Почему важен |
|---|---|---|
| Q1 | Задумана ли корзина анонимной, и является ли `cart_id` фактически bearer-секретом? | Если да, его утечка = чужой заказ (BUG-04); если нет - отсутствует контроль доступа |
| Q2 | Должен ли остаток уменьшаться при создании заказа и что происходит при отмене? | Без этого нельзя отличить отрицательный остаток (BUG-02) от особенности |
| Q3 | Допустим ли заказ на нулевую сумму (например, полностью покрытый скидкой)? | От этого зависит ожидаемый результат TC-22 / BUG-03 |
| Q4 | Должна ли кнопка «Confirm» срабатывать с первого нажатия? | BUG-05 может быть дефектом или недокументированным двухфазным подтверждением |
| Q5 | Нужна ли проверка остатка при добавлении в корзину или только при оплате? | Влияет на то, где должен стоять валидатор и какой код ответа ожидать |
| Q6 | Должен ли `migrate:fresh --seed` очищать кеш каталога? | Сейчас документированная процедура сброса ломает add-to-cart на 5 минут (BUG-06) |

## 7. Что не проверено

- **Конкурентные заказы последнего экземпляра** (гонка при остатке 1):
  требует точной синхронизации, вне бюджета.
- **Отмена/возврат заказа и влияние на остаток**: функциональности отмены
  в области проверки нет.
- **Гостевое оформление** (TC-27): отдельная ветка checkout, не покрыта.
- **Способы оплаты bank-transfer / credit-card / gift-card** (TC-28): не покрыты,
  проверен только cash-on-delivery.
- **Скидки** (TC-29): eco-discount и additional discount не проверялись.
- **Firefox / WebKit**: проекты не заведены, прогон не выполнялся.
- **Восстановление пароля, 2FA, профиль**: вне области.
- **Отказ postcode-сервиса**: в коде есть fail-open, но сценарий отказа
  бэкенда не воспроизводился.
- **Нагрузка и rate limiting**: вне области.

## 8. Критерии выхода

Релиз проверенной части считается готовым, если:

1. Критический путь «товар - корзина - заказ» проходит и через API, и через UI.
2. Суммы и позиции заказа совпадают с корзиной.
3. Нет открытых дефектов Critical/High в области проверки.
4. Известные дефекты Medium задокументированы и приняты продуктом.

Фактический результат - в `RELEASE.md`.
