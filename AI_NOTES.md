# AI_NOTES - как использовался AI

Задание требует полной истории AI-сессий и честного описания того, что AI
предложил, что было проверено, что исправлено и что осталось за пределами записи.

## 1. Инструменты и модели

| Что | Значение |
|---|---|
| AI-инструмент | DeepSeek Harness (Web GUI), агентный режим с доступом к shell, файлам и Docker |
| Модель | `deepseek-flash` |
| Инлайн-автодополнение в редакторе | **Не использовалось** |
| Субагенты / workflow-оркестрация | Не использовались - вся работа в одной сессии |
| Облачные агенты без экспорта | Не использовались |
| Инструменты, которые вызывал агент | `bash`, чтение/запись файлов, `grep`/`glob`, Docker CLI, Playwright CLI, `curl`, `jq` |
| Файлы инструкций для агентов (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`) | Не создавались: агент работал в сессии без постоянных инструкций |

PDF с заданием разбирался программно (`pypdf`), а не «на глаз»: агент прочитал
5 страниц, включая требования к тест-кейсам, дефектам, AI-сессиям и отчёту.

## 2. Список сессий

Файлы экспорта - в `ai_sessions/`.

| Файл | Инструмент | Задача | Что появилось из этой сессии |
|---|---|---|---|
| `01-toolshop-sprint5-session.jsonl` + `.md` | DeepSeek Harness, `deepseek-flash` | Вся работа целиком: разбор ТЗ, выбор версии, развёртывание, анализ приложения, каркас, API- и UI-автотесты, поиск и подтверждение дефектов, документы, финальный прогон и отчёт | Все файлы репозитория: `README.md`, `TEST_PLAN.md`, `TEST_CASES.md`, `BUGS.md`, `RELEASE.md`, `AI_NOTES.md`, `playwright.config.ts`, `tsconfig.json`, `package.json`, `.env.example`, `.gitignore`, `src/**`, `tests/**`, `scripts/**`, `reports/**`, `ai_sessions/**` |

Сессия одна: работа велась подряд, без переключения инструментов. Отдельных
сессий на «развёртывание», «тесты» и «дефекты» не заводилось, поэтому история
линейна: 9 запросов, 27 шагов ассистента, 65 вызовов инструментов, 244 события.

**Что делалось без AI.** Выбор версии `sprint5`, приоритеты и границы проверки
сформулированы агентом в сессии и проверены человеком при ревью. Вне записи
остались только финальное чтение репозитория человеком и решение о публикации.
Развёртывание, прогоны и ручные пробы выполнялись командами агента в этой же
сессии - отдельных действий вне записи не было.

## 3. Как проверялся результат AI

Правило: **любое утверждение AI о поведении продукта считается гипотезой до тех
пор, пока не воспроизведено командой и не подтверждено ответом API, БД или
trace.**

| Что предложил AI | Как проверялось | Итог |
|---|---|---|
| «В `sprint5-with-bugs` есть корзина и оформление» | Сравнены каталоги `checkout`: в `sprint5` есть `cart`, `login`, `address`, `payment`; в `sprint5-with-bugs` только `checkout` | Утверждение неверно, выбрана `sprint5` |
| «`POST /carts/{id}` вернёт 201» | Первый прогон: 200. Ожидание в тесте исправлено | 200 |
| «У товара есть поле `stock`» | Ответ API: поля нет, есть `in_stock: boolean`; исправлены интерфейс и фикстура | Только `in_stock` |
| «Поиск сломан: на `hammer` возвращается 45 товаров» | Повторный замер с ожиданием замены карточек: 6 товаров, все содержат `hammer` | Ложное срабатывание, тест переписан на `expect.poll` |
| «`in_stock` в списке и карточке расходится - отдельный дефект» | Воспроизведено: список из кеша 300 с отдаёт `true`, карточка - `false`; причина - кеш, а не разные источники данных | Наблюдение TC-26, отдельный дефект не заводился |
| «Confirm создаёт заказ с первого нажатия» | Trace и скриншот: после первого клика `POST /invoices` не уходит, заказ появляется только после второго | BUG-05 подтверждён |
| «Счётчик результатов поиска отстаёт - это баг» | Наблюдение подтверждено, но классифицировано как UX-замечание | В `BUGS.md`, раздел «Наблюдения» |
| «Количество в корзине ограничено 99» | Прочитан `CartController`: `min:1|max:99` | Подтверждено |
| «Аккаунт блокируется после трёх неудачных входов» | Ручная проверка на отдельном пользователе: 401, 401, 401, затем 423 | TC-30 пройден |
| «`migrate:fresh --seed` достаточно для сброса» | После reseed `GET /products` отдал старый id, add-to-cart - 422; после `cache:clear` - 200 | BUG-06 подтверждён |

Дополнительно каждый автотест проверялся не «зелёным цветом», а тем, что он
**падает на сломанном поведении**: пять тестов на дефекты помечены `test.fail()`
и падают ожидаемо, а корректность остальных подтверждена тем, что при первом
прогоне они падали на реальных расхождениях с контрактом (200 вместо 201,
`in_stock` вместо `stock`, видимость sign-out, отложенный пересчёт итога).

## 4. Что в предложениях AI было исправлено или отклонено

| # | Предложение AI | Решение | Причина |
|---|---|---|---|
| 1 | Взять `sprint5-with-bugs` (интереснее искать баги) | **Отклонено** | Нет шагов корзины и адреса - обязательную цепочку не пройти; плюс в репозитории опубликован список багов, работа по нему выглядела бы как заимствование |
| 2 | Использовать демо-аккаунты из README приложения | **Отклонено** | Аккаунт блокируется после 3 неудачных входов (проверено, TC-30); общий пользователь обрушил бы негативные тесты |
| 3 | Сбрасывать БД в `globalSetup` через `migrate:fresh --seed` | **Отклонено** | Скрывает загрязнение данных и добавляет 30+ с к прогону; тесты сделаны независимыми, сброс описан как подготовка |
| 4 | `test.fail()` на уровне `describe` | **Исправлено** | Помечает все тесты блока; перенесено внутрь каждого теста |
| 5 | Проверять успешный логин по видимости `nav-sign-out` | **Исправлено** | Элемент в свёрнутом dropdown: attached, но не visible; заменено на `toBeAttached` + уход с `/auth/login` |
| 6 | Клик по `add-to-cart` сразу после `goto` | **Исправлено** | Клик в окно до отрисовки - «тихий» no-op без `POST /carts`; добавлены ожидание заголовка, доступности кнопки и счётчика |
| 7 | Адрес «Amsterdam / 1011AB» в тестовых данных | **Исправлено** | Локальный lookup отдаёт для 1011AB город Stroe; API отвечал 422 «city does not belong to the country». Адрес строится из `GET /postcode-lookup` |
| 8 | Проверять итог корзины сразу после ввода количества | **Исправлено** | Сервер пересчитывает итог после round-trip; проверка переведена на `expect.poll` |
| 9 | Матчеры `toBeWithin` / `toBeOneOf` прямо в тестах | **Исправлено** | В Playwright таких матчеров нет; добавлен `src/fixtures/matchers.ts` с `expect.extend` и типами |
| 10 | Заявлять в README время «4 часа» | **Отклонено** | Журнал заполнен по фактическим таймстампам; завышать так же плохо, как занижать |
| 11 | Оставить дефекты только в тексте, без автотестов | **Отклонено** | Задание требует оставить тесты, воспроизводящие дефекты, и пометить их |
| 12 | Ждать от `POST /carts/{id}` ответ 201 | **Исправлено** | Реальный ответ - 200; ожидание исправлено после первого прогона |
| 13 | Читать остаток из поля `stock` | **Исправлено** | Клиентский API отдаёт только `in_stock`; модель переписана |

## 5. Пробелы записи и маскирование

### Пробелы

- Экспорт - это журнал инструмента: 244 события, включая каждый запрос, ответ
  ассистента, вызов инструмента и его результат. `.jsonl` содержит полные
  значения, `.md` - читаемый рендер того же журнала; в нём длинные аргументы и
  результаты сокращены и помечены `…`. Рендер не заменяет экспорт.
- Снимок снят **2026-11-03 23:06 UTC (00:06 CET)**, сразу после записи
  `AI_NOTES.md`. Всё, что было раньше, включая финальный прогон и отчёт, в
  журнале есть.
- После снятия снимка остались только упаковка в git (коммиты по блокам),
  публикация и, при необходимости, правка журнала времени в README. Код тестов,
  конфигурация и `reports/` после снимка не менялись; если README/журнал
  поправлены - это оформление, а не результаты проверки.
- Пробный экспорт «на короткой сессии» до начала работы не делался. Формат
  подтверждён по факту: экспорт снят после финального прогона и проверен на
  читаемость.
- Неудачные попытки в журнале сохранены: первый прогон API с двумя падениями,
  первый прогон UI с двумя падениями, неверное ожидание 201, `stock` вместо
  `in_stock`, `test.fail` на уровне `describe`, ложное срабатывание по поиску.

### Маскирование

Заменялись только значения, сообщения и вызовы инструментов не удалялись:

| Что заменено | Сколько раз | На что |
|---|---|---|
| Домашний путь пользователя `/Users/<имя>` | 5 | `<REDACTED: домашний путь пользователя>` |
| Токены доступа | 0 (в экспорт не попали) | в примерах команд используется плейсхолдер `<TOKEN>` |

Учётные данные самого Toolshop (`admin@…`, `customer@…` / `welcome01`) не
маскировались: они публичны и перечислены в README проекта.

## 6. Оценка работы с AI

Что AI сделал хорошо: разобрал PDF и репозиторий приложения, быстро собрал
каркас и основную часть тестов, провёл серию проб и локализовал шесть дефектов,
свёл результаты в документы и отчёт.

Где AI был ненадёжен и потребовалась проверка: **все** первые предположения о
кодах ответа и полях API оказались неверными при первом прогоне; два «дефекта»
оказались артефактами тестов (ложное срабатывание по поиску и расхождение
`in_stock`, вызванное кешем); несколько раз тесты были зелёными по неправильной
причине (клик в пустоту, сэмплирование DOM до обновления, неполный адрес).
Зелёный прогон ни разу не был доказательством корректности - доказательством
были ответы API, база данных и trace.
